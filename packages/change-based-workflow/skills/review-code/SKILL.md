# Review-Code — AI 审查 + 人类审查

对照 tasks.md 和 plan.md，AI 审查代码变更，然后启动 Plannotator 人类审查。

## 输入

- 变更范围：`$CHANGE_DIR/change.md` 最新「编码完成」节的文件清单
- 计划范围：`$CHANGE_DIR/tasks.md` 子任务清单
- 目标来源：`$CHANGE_DIR/plan.md`

## 审阅流程

### 1. 确定审阅轮次

读取 change.md，统计已有「代码审阅」节数，当前为第 N 轮。最多 3 轮。

### 2. AI 审查

逐项检查，发现问题分级处理：

#### 范围偏差

实际改动是否和 task 描述一致？有没有夹带无关重构、偷加新依赖、顺手删了别的代码？

#### 🔴 硬性阻断（有一条即不可交付）

- **注入漏洞**：SQL、命令、路径注入
- **凭证泄露**：密钥、token 硬编码或提交
- **依赖变更**：新增/升级了 plan.md 未声明的依赖
- **破坏性操作**：删除或重命名了计划外的现有文件/接口

#### 🟡 模式补全

如果修复了一个"某处缺校验"的 bug，grep 全项目看有没有同类遗漏。同一模式多处存在时列出未处理项。

#### 🟡 文档债

这次改动是否引入了该写进 AGENTS.md 但还没写的规则？

#### Autofix 分级

| 级别 | 例子 | 操作 |
|------|------|------|
| 安全自动 | 拼写错误、缺 import、格式不一致 | 直接修 |
| 需确认 | 加了 null 检查、改了错误处理逻辑 | 列出等你确认 |
| 需判断 | 架构问题、安全权衡 | 标注，留给人类审 |

安全自动的直接修，需确认的列出等判断。

### 3. 根因追问

修完问一句：什么架构改动可以防止这类 bug 再出现？如果答案有价值，推荐运行 `/improve-architecture`。

### 4. Plannotator 人类审查

```bash
plannotator review
```

你在浏览器中可视化审阅 diff，标注问题。反馈直接作为修复输入。

## 审阅报告格式

```markdown
---

# 变更 v{N}：代码审阅（第 N' 轮）

## 审查信息

- 审阅轮次：第 N' / 3 轮
- 变更文件数：N

## 范围偏差

| # | 文件 | 问题 |
|---|------|------|

## 硬性阻断

| # | 类别 | 位置 | 问题 |
|---|------|------|------|

## 模式补全

| # | 模式 | 未处理位置 |
|---|------|-----------|

## 文档债

| # | 应写规则 | 目标文件 |
|---|---------|---------|

## Autofix

| # | 级别 | 文件 | 修复 | 状态 |
|---|------|------|------|------|

## 根因追问

- 问题：什么架构改动可以防止再出现？
- 建议：{如有，推荐 /improve-architecture}

## 总体结论

- **可交付判定**：是 / 否
```

## 停止条件

- 无可审阅基线 → 停止
- 审查完成 + Plannotator 反馈处理完毕 → 停止
