# FRD: Footer 推理速度与 TTFT 常驻显示

## Summary

新建 pi 扩展包 `@cnife/pi-inference-speed`，在 pi footer 状态栏常驻显示当前 LLM 推理速度（TPS，tokens/s）和首 token 延迟（TTFT，秒），格式 `TPS123.4T/s TTFT1.2s`。TPS 用单条 assistant message 的 output tokens / 该 message elapsed（参考 `tps.ts` 的 output/elapsed 公式），TTFT 用流式事件精确计时（`before_provider_request` → 首任意 `_delta`）。每条 assistant message 结束后 footer 显示该条 TPS/TTFT 直到下一条，无配置文件。

## Problem & Intent

开发者原话意图：“量化体感/满足好奇”——单纯想知道当前这次 LLM 到底跑了多快、首字等了多久，让等待可量化。不是为模型选型横评，也不是为延迟异常监控，而是把每条 message 的推理速度和首字延迟变成 footer 里一眼可见的数字，满足对推理过程的好奇心。

## Goals

- 在 pi footer 常驻显示当前 assistant message 的 TPS（tokens/s）和 TTFT（秒），格式 `TPS123.4T/s TTFT1.2s`
- TPS 反映单条 assistant message 的推理速度（output tokens / 该 message elapsed），公式与 `tps.ts` 的 output/elapsed 一致
- TTFT 精确到首 token（含 thinking/toolcall 任何 delta），用流式事件计时，起点为请求真正发出（`before_provider_request`）
- 每条 assistant message 结束后 footer 保持该条 TPS/TTFT，直到下一条 message 结束刷新
- 复刻 cache-hit-rate 的 footer 常驻 + 会话事件重建机制

## Non-Goals

- 不做颜色阈值配置（无 colorRules，无配置文件）——YAGNI，"满足好奇"场景数字本身已够
- 不做模型横向对比/历史统计/累计平均——单轮瞬时指标即可
- 不做延迟异常告警/监控
- 不做生成中实时速度——message 结束后显示最终值，不在生成中刷新
- 不替换 `~/github/pi/.pi/extensions/tps.ts` 的 notify 弹通知行为（那是另一仓库的独立扩展，本包是 pi-extensions 的新包，互不影响）

## Functional Requirements

1. 系统 SHALL 在 pi footer 用 `ctx.ui.setStatus` 固定 key 常驻显示 `TPS<n>T/s TTFT<n>s` 格式文本
2. 系统 SHALL 在 `before_provider_request` 事件触发时记录请求起点时间戳 `requestAt = Date.now()`
3. 系统 SHALL 在 `message_update` 事件首次出现 `assistantMessageEvent.type` 以 `_delta` 结尾时记录首 token 时间戳 `firstDeltaAt = Date.now()`
4. 系统 SHALL 计算 `TTFT = (firstDeltaAt - requestAt) / 1000`，单位秒，保留 1 位小数
5. 系统 SHALL 在 `message_end`（assistant）时计算 `TPS = usage.output / elapsed`（elapsed 为该条 message 的起止时间差，单位 tokens/s，保留 1 位小数），公式参考 `tps.ts`
6. 系统 SHALL 在每条 assistant message 的 `message_end` 后用该条 TPS/TTFT 更新 footer，并保持显示直到下一条 message 结束
7. 系统 SHALL 在 `session_start`/`session_tree`/`session_compact`/`model_select` 时重置/重建显示状态，避免跨会话/模型/分支残留错误值
8. 系统 SHALL 在无数据时显示占位 `TPS--.-T/s TTFT -.-s`，用 dim 色

## Non-Functional Requirements

- **Performance**: footer 更新在事件 handler 内同步完成，无异步阻塞；流式 `message_update` 仅在首次 `_delta` 时记时间戳一次，后续 delta 不重复计算
- **Security**: 无外部网络/文件写入（无配置文件），不处理敏感数据
- **UX / Accessibility**: footer 文本简洁单行，与 cache-hit-rate 风格一致；无数据时占位可读
- **Reliability**: 事件缺失或时序异常（如未收到 `before_provider_request` 就收到 delta）时降级为占位显示，不抛错；时间戳为 0 或负值时显示占位

## Constraints & Assumptions

- 技术约束：peerDependencies `@earendil-works/pi-coding-agent`（不引入运行时依赖）；TypeScript + Biome（双引号 2 空格）；包结构遵循 `packages/AGENTS.md`
- 技术假设：`before_provider_request` 事件在一轮首次 provider 调用时触发且 handler 内 `Date.now()` 可作为请求发出时刻（probe 未确认该事件 payload 有 timestamp 字段，用 `Date.now()` 取代）——research 需验证
- 技术假设：`message_update` 的 `assistantMessageEvent.type` 以 `_delta` 结尾可覆盖 `text_delta`/`thinking_delta`/`toolcall_delta` 等所有 token 增量变体——research 需验证 pi-ai 流协议联合类型的完整变体清单
- 技术假设：一次 turn 可能含多条 assistant message（多步 agent），每条 message 各自计算 TPS/TTFT；TTFT 取该条 message 的 request → 首次 delta——research 需验证多步 agent 下 `before_provider_request` 与 `message_end` 的配对关系
- 部署约束：用 feature branch 开发流程（建 feature branch → 开发 → 合并 main → `git push` → `pi update`），本地测试用 `pi -ne -ns -e packages/inference-speed/extensions/inference-speed.ts`

## Acceptance Criteria

- [ ] `packages/inference-speed/` 目录存在，含 `package.json`（name `@cnife/pi-inference-speed`，`pi.extensions` 指向 `./extensions`）、`README.md`、`extensions/inference-speed.ts`
- [ ] `pi -ne -ns -e packages/inference-speed/extensions/inference-speed.ts` 启动后 footer 出现 `TPS--.-T/s TTFT -.-s` 占位
- [ ] 发送一条消息，LLM 回复结束后 footer 显示 `TPS<正数>T/s TTFT <正数>s`（数值非占位）
- [ ] TTFT 数值小于该条 message 耗时（首 token 早于 message 结束）
- [ ] 切换模型（/model）后 footer 重置为占位，新 message 结束后显示新值
- [ ] 多步 agent 或多轮对话中 footer 始终显示最近一条 message 的 TPS/TTFT
- [ ] 无配置文件生成（`~/.pi/agent` 下无 `cnife-inference-speed.json`）
- [ ] TypeScript 编译 + Biome format 检查通过

## Recommended Approach

新建独立包 `packages/inference-speed/`（`@cnife/pi-inference-speed`），单文件扩展 `extensions/inference-speed.ts`，默认导出 `(pi: ExtensionAPI) => void`。复刻 cache-hit-rate 的 `ctx.ui.setStatus` 常驻 + `session_*`/`model_select` 重建骨架，新增 `before_provider_request`（记 `requestAt`）、`message_update`（首次 `_delta` 记 `firstDeltaAt`）、`message_end`（算 TPS 并发布）三个 handler。无配置文件、无颜色逻辑。TPS 公式参考 `~/github/pi/.pi/extensions/tps.ts`（output/elapsed），TTFT 口径用流式事件精确计时。

## Decisions

### TTFT 实现方案

**Question**: 从探测推断 TTFT 可用流式事件精确计时（`message_update` 的 `text_delta`），保留精确流式方案还是改近似/暂不做？
**Recommended**: 保留精确流式方案
**Chosen**: 保留精确流式方案
**Rationale**: probe 证实 `node_modules/@earendil-works/pi-ai/dist/types.d.ts:249-301` 定义流协议联合类型含 `text_delta`/`thinking_delta` 等，agent-loop 收到 stream delta 后 emit `message_update`，可精确到首 token；近似方案（`turn_start`→`message_end`）含整回合生成时间不是真 TTFT

### 显示时机（最终值 vs 实时）

**Question**: TPS/TTFT 是单条 message 的瞬时指标，footer 该在 message 结束后显示最终值还是生成中实时显示？
**Recommended**: message 结束后显示最终值
**Chosen**: message 结束后显示最终值
**Rationale**: 复刻 `packages/cache-hit-rate/extensions/cache-hit-rate.ts:352` 的 `setStatus` 常驻 + 重建语义最简；生成中实时需处理 `partial.usage` 实时性，复杂度高且"满足好奇"用最终值已够

### 刷新粒度（message vs turn）

**Question**: FRD 里“轮”概念含糊（概述说“轮结束”，FR #6 说 message_end），pi 有 turn_end（回合结束）和 message_end（每条 assistant message）两种粒度，TPS/TTFT 用哪种刷新？
**Recommended**: message 粒度（message_end 触发）
**Chosen**: message 粒度（message_end 触发）
**Rationale**: optimizes 体感即时性 + agent 多步 tool use 时每步可见速度；`packages/cache-hit-rate/extensions/cache-hit-rate.ts:397` 即 message_end 更新先例；turn 粒度在多步 agent 时 footer 长时间不变且 tool 执行时间稀释 TPS

### TTFT 计时口径

**Question**: TTFT 起点与首 token 定义的口径组合？
**Recommended**: 体感口径（`turn_start` → 首 `text_delta`）
**Chosen**: `before_provider_request`（请求发出）→ 首任意 `_delta`（含 thinking/toolcall）
**Rationale**: 开发者选业界标准网络 TTFT 定义——排除本地 system prompt 组装的纯网络+排队延迟，首 token 含 thinking/toolcall 任何 delta 更贴合"模型开始产出"。实现：`before_provider_request` handler 记 `requestAt = Date.now()`，`message_update` 首次 `assistantMessageEvent.type` 以 `_delta` 结尾记 `firstDeltaAt`

### TPS 计算口径

**Recommended**: n/a — 用户输入指定
**Chosen**: 单条 message 的 output tokens / 该 message elapsed（`tps.ts` 的 output/elapsed 公式）
**Rationale**: evidence: `/home/cnife/github/pi/.pi/extensions/tps.ts:43` `output/elapsedSeconds` 公式；统计范围按 message 粒度决策定为单条 message，用户明确指定参考

### 配置项

**Question**: TPS/TTFT 是否需要颜色阈值配置（像 cache-hit-rate 的 colorRules）？
**Recommended**: 无配置
**Chosen**: 无配置
**Rationale**: 意图"量化体感/满足好奇"下数字本身已够，YAGNI 颜色阈值；避免 loadConfig + 校验 + 配置文件复杂度

### 包名与结构

**Question**: 新包 npm 包名与目录？
**Recommended**: `@cnife/pi-speed`
**Chosen**: `@cnife/pi-inference-speed`（目录 `packages/inference-speed/`）
**Rationale**: 描述性最强，明确“推理速度”涵盖 TPS 与 TTFT；结构复刻 `packages/cache-hit-rate/`（package.json + README + extensions/<name>.ts + peerDeps，见 `packages/cache-hit-rate/package.json:23-30`）

### footer 机制与事件重建

**Question**: （用户输入隐含指定——"底部状态栏参考 cache-hit-rate"）
**Recommended**: n/a — 用户输入指定
**Chosen**: `ctx.ui.setStatus` 固定 key 常驻 + `session_start`/`session_tree`/`session_compact`/`model_select` 重建 + `message_end` 刷新
**Rationale**: evidence: `packages/cache-hit-rate/extensions/cache-hit-rate.ts:352,373-431`，用户明确指定参考
