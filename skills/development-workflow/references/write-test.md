# write-test 阶段 — 完整操作说明

## 输入

- **变更范围**：`$CHANGE_DIR/change.md` 最新变更摘要中的文件清单
- **上下文**：`$CHANGE_DIR/tasks.md`、`$CHANGE_DIR/plan.md`

## 测试范围界定

本阶段负责的测试类型：

| 测试类型 | 职责 | 时机 |
|---------|------|------|
| 单元测试 | 验证单函数/单模块逻辑 | write-code 阶段（每片自验证时）|
| 集成测试 | 验证跨模块/跨切片交互 | **本阶段** |
| E2E 验收测试 | 验证端到端用户场景 | **本阶段** |

本阶段专注于**集成测试和 E2E 验收测试**。单元级测试在 write-code 阶段完成。
如果 change.md 的「编码完成」节未标注单元测试覆盖，在本阶段补充。

## 流程

1. 读取 change.md，定位最新变更摘要节（「编码完成」或「修复完成」），提取变更文件清单
2. 读取 tasks.md，了解各任务的验证方式
3. **确定测试范围**：变更了哪些模块/函数，就为哪些模块/函数写测试——而非一刀切只测最上层
4. **编写测试**：
   - 每个被修改的函数至少一条正向用例
   - 边界情况：空输入、极值、异常路径
   - 集成测试覆盖跨切片交互场景
   - E2E 测试覆盖端到端用户流程
   - 测试文件放在 `tests/` 目录（或项目约定的测试目录），命名对应源文件
5. **运行项目的测试命令**（如 `pytest`、`npm test`、`cargo test` 等），确保全部通过
6. 若失败 → 修复测试代码，最多 3 次尝试
7. 追加测试记录到 change.md

## 验证规则

- 测试必须全部通过（退出码 0）
- 用例数 > 0（避免空测试文件）
- 失败时根据错误信息修复，最多重试 3 次

## 输出格式

向 `$CHANGE_DIR/change.md` 追加：

```markdown
---

# 变更 v{N}：测试编写

## 测试文件

| 文件 | 对应源码 | 用例数 |
|------|---------|--------|
| tests/test_a.py | src/a.py | 5 |

## 测试覆盖

| 测试类型 | 数量 |
|---------|------|
| 正向用例 | 3 |
| 边界情况 | 1 |
| 异常路径 | 1 |

## 验证结果

- （项目的测试命令）：通过（N passed）
```

### STATE 更新

追加测试记录后，更新 change.md 顶部的 STATE 块（当前阶段、已完成项）。

## 停止条件

- 变更范围无法确定 → 输出说明并停止
- 测试全部通过且记录追加完毕 → 停止
- 3 次修复后测试仍失败 → 输出失败详情并停止
