# review-code 阶段 — 完整操作说明

## 输入

- **变更范围来源**：`$CHANGE_DIR/change.md` 最新变更摘要中的文件清单
- **计划范围来源**：`$CHANGE_DIR/tasks.md` 子任务清单「涉及文件」列
- **目标来源**：`$CHANGE_DIR/plan.md`「目标」节
- **上下文**：`$CHANGE_DIR/change.md` 已有审阅记录

## 审阅流程

1. **确定审阅轮次**：读取 change.md，统计已有「代码审阅」节数，当前为第 N 轮。N=1 时基线为最新「编码完成」节，N>1 时基线为最新「修复完成」节。若 N=3，标注为最终审阅。
2. **确定审查范围**：
   - N=1：以 tasks.md「涉及文件」列为全量范围
   - N>1：仅审阅「修复完成」节的变更文件清单中的文件，但 Hard Stops 和代码质量检查仍覆盖全项目
3. **目标完成度检查**：对照 plan.md「目标」—— ✅ 已实现 / ⚠️ 部分实现 / ❌ 未实现 / ➕ 超出目标
4. **范围审阅**：逐文件对照 tasks.md「涉及文件」列，标注 ✅ 符合 / ❌ 超出范围
5. **垂直切片完整性检查**（新增）：如果 tasks.md 按垂直切片拆分，检查每个切片的「涉及文件」是否覆盖了该切片穿透的所有层（schema、API、逻辑、页面、验证等）。如果某层缺失，标注 🟡 建议。
6. **Hard Stops 检查**（🔴 阻断级，有一条即不可交付）：
   - 注入漏洞：SQL、命令、路径注入
   - 凭证泄露：密钥、token 硬编码或提交
   - 依赖变更：新增/升级了 plan.md 未声明的依赖
   - 破坏性操作：删除或重命名了计划外的现有文件/接口
7. **调试质量检查**（新增，仅当 change.md 最新节是"修复完成"时）：
   - 根因声明是否存在？是否精确到文件:行号？缺失→🔴 阻断
   - 是否添加了回归测试来防止同类问题再出现？缺失→🟡 建议
   - 修复是针对根因还是症状？症状修复→🟡 建议
8. **运行 Format 检查**（如 `ruff format --check`、`npm run format` 等）
7. **运行 Lint 检查**（如 `ruff check`、`eslint` 等）
9. **修复循环**（仅 format/lint，最多 2 轮）：不通过则自动修复后重新检查；2 轮后残留记录到「未通过项详情」
10. **问题分级汇总**：🔴 阻断（Hard Stops + 超出范围 + 缺根因）/ 🟡 建议（部分实现 + 切片不完整 + lint 残留 + 缺回归测试）/ 🔵 注意（格式残留）
11. **追加审阅报告**到 change.md

## 输出格式

向 `$CHANGE_DIR/change.md` 追加：

```markdown

- 审阅时间：YYYY-MM-DD
- 审阅轮次：第 N' / 3 轮
- 变更文件数：N
- 审查基线：{编码完成 / 修复完成}

## 目标完成度

- 状态：✅ / ⚠️ / ❌
- 说明：{对照 plan.md「目标」的完成情况}

## 范围审阅

## 切片完整性

|---|--------|--------|------|

| # | 类别 | 位置 | 问题 |

|---|--------|------|------|
| 1 | 根因声明 | ✅ / ❌ | |
```

## 下一步指引

- **可交付** → 进入 write-test
- **不可交付 且 N<3** → 进入 fix-code
- **不可交付 且 N=3** → 审视方案，可能回到 write-plan

## 约束

- 仅执行文件读取、命令运行、自动修复和报告写入，不做 AI 代码编辑
- Hard Stops 有一条即判不可交付
- 格式检查和 lint 检查独立于范围审阅

## 停止条件

- change.md 中无可匹配的基线节 → 停止
- tasks.md 或 plan.md 不存在 → 停止
- 修复循环超过 2 轮 → 记录残留，追加报告并停止
- 所有检查完成、报告追加完毕 → 停止
