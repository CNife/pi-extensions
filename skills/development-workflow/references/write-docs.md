# write-docs 阶段 — 完整操作说明

## 输入

- **变更历程**：`$CHANGE_DIR/change.md` 全部内容
- **上下文**：`$CHANGE_DIR/plan.md`、`$CHANGE_DIR/tasks.md`

## 文档分类

本次变更产生的文档分为两类：

| 类型 | 说明 | 维护时机 | 位置 |
|------|------|---------|------|
| **内联文档** | 术语表 (glossary)、架构决策 (ADR) | 开发过程中维护 | `changes/<change>/glossary.md`、`docs/adr/` |
| **发布文档** | README、AGENTS.md、docs/ | write-docs 阶段 | 项目原位置 |

本阶段职责：
1. 审查内联文档是否需要升级（glossary → AGENTS.md 合并、ADR 确认）
2. 产出发布文档（README、docs/ 等）

## 流程

1. 读取 change.md 完整内容，理解本次变更做了什么
2. **审查内联文档是否需要升级**：
   - `$CHANGE_DIR/glossary.md` 中的重要术语是否已合并到项目级 `AGENTS.md`？
   - 开发过程中产生的 ADR 是否已就位？
   用户确认后执行升级。
3. 列出项目中可能受影响的发布文档：
   - `README.md` — 项目简介、安装说明、快速开始
   - `AGENTS.md` — AI 协作规范（文件地图、开发规则、已知问题）
   - `docs/` — 补充文档
   - 项目根目录其他 `.md` 文件
4. **逐文件判断是否需要更新**，向用户展示：

   ```
   文档影响评估：

   | 文件 | 影响 | 建议 |
   |------|------|------|
   | README.md | 无 | 不更新 |
   | AGENTS.md | 有：流水线新增步骤 | 更新「已知问题」或「当前进度」 |
   ```

5. 用户确认后，逐一更新需要修改的文档
6. 追加文档更新记录到 change.md

## 更新原则

- 只修改与本次变更直接相关的内容，不动无关章节
- 修改已有文件时用精确的文本替换，不重写整个文件
- 新增内容保持与现有文档一致的风格和结构
- 删除过时信息（如旧的步骤描述），但保留历史引用

## 输出格式

向 `$CHANGE_DIR/change.md` 追加：

```markdown
---

# 变更 v{N}：文档更新

## 更新的文档

| 文件 | 变更类型 | 说明 |
|------|---------|------|
| README.md | 修改 | 更新流水线步骤说明 |
| AGENTS.md | 修改 | 更新已知问题 |
```

### STATE 更新

追加文档记录后，更新 change.md 顶部的 STATE 块（当前阶段、已完成项）。

## 停止条件

- 用户确认无文档需要更新 → 停止
- 所有需要更新的文档已更新且记录追加完毕 → 停止
