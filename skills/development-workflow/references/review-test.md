# review-test 阶段 — 完整操作说明

## 输入

- **测试记录**：`$CHANGE_DIR/change.md` 最新「测试编写」节
- **变更范围**：`$CHANGE_DIR/change.md` 最新变更摘要中的文件清单
- **上下文**：`$CHANGE_DIR/tasks.md`、`$CHANGE_DIR/plan.md`

## 审阅流程

1. 定位最新「测试编写」节，统计已有「测试审查」节数，当前为第 N 轮（最多 2 轮）
2. 读取测试文件，逐文件审查：
   - **格式检查**：测试命名、结构是否符合项目规范
   - **断言有效性**：是否有有意义的断言（禁止 `assert True`、空断言等占位）
   - **覆盖率**：变更的函数是否至少各有一条用例
   - **边界覆盖**：是否覆盖了关键边界和异常路径
   - **用例独立性**：测试用例之间是否有顺序依赖
3. **运行项目的测试命令**，确认全部通过
4. 问题分级：
   - 🔴 阻断：用例全部失败、测试文件有语法错误、零用例
   - 🟡 建议：缺少边界用例、断言不够精确、部分变更函数未覆盖
   - 🔵 注意：命名不规范、注释缺失
5. 追加审查报告到 change.md

## 输出格式

向 `$CHANGE_DIR/change.md` 追加：

```markdown
---

# 变更 v{N}：测试审查（第 N' 轮）

## 审查信息

- 审阅时间：YYYY-MM-DD
- 审阅轮次：第 N' / 2 轮
- 测试文件数：N
- 总用例数：N

## 审查结果

| # | 测试文件 | 用例数 | 状态 | 问题 |
|---|---------|--------|------|------|

## 总体结论

- **可交付判定**：是 / 否
- 阻断项：{如有，逐条}

## 不通过项详情

| # | 严重程度 | 文件 | 问题 | 处理建议 |
|---|---------|------|------|---------|
```

## 下一步指引

- **可交付** → 进入 write-docs
- **不可交付 且 N<2** → 回到 write-test 修复
- **不可交付 且 N=2** → 审查已达上限：有 🔴 阻断则停止；仅有 🟡 建议则记录残留，继续进入 write-docs

## 约束

- 不修改测试代码
- 断言有效性是核心标准
- 即使审查未通过，仍须完成所有检查并追加报告

## 停止条件

- 变更范围无法确定 → 停止
- 所有检查完成、报告追加完毕 → 输出下一步指引并停止
