# write-code 阶段 — 完整操作说明

## 输入

- **主输入**：`$CHANGE_DIR/tasks.md` — 任务拆解与分层计划
- **上下文**：`$CHANGE_DIR/plan.md` — 变更方案全文

## 执行流程

```
读取 tasks.md → 解析 wave 列表
  ↓
对每一层 wave：
  对层内每个任务（按 ID 顺序）：
    1. 编码：按任务描述实现变更
    2. 验证：运行该任务的验证命令
    3. 通过 → 下一个任务；失败 → 修复（最多 3 次）
  该层全部通过 → 进入下一层
  ↓
所有 wave 完成 → 输出完成总结
```

## 编码规则

- 每个任务只修改其「涉及文件」列指定的文件，不动无关代码
- 修改已有文件时，用精确的文本替换（oldText → newText），不重写整个文件
- 新建文件时，确认父目录存在
- 多个任务修改同一文件时，后续任务在前序任务的基础上修改
- 遇到 plan.md 和 tasks.md 之间存在歧义时，以 plan.md 为准

### 反馈环优先原则

当任务涉及以下任何情况时，第一步不是写实现代码，而是先构建反馈环（快速 pass/fail 信号）：

- 不熟悉的技术栈或工具
- 外部 API / 服务依赖
- 首次在该项目中使用的构建/测试工具
- 难以直觉判断正确性的逻辑

反馈环示例：
- 编译脚本（确认环境就绪）
- 最小测试（确认新工具链可运行）
- curl / ping 命令（确认外部 API 可达）
- 空函数 + 测试（确认测试框架能发现失败）

反馈环构建完成后，再开始写实现代码。反馈环本身不废除，后续验证可以复用。

## 验证规则

- 验证命令直接来自 tasks.md 子任务清单的「验证方式」列
- 每完成一个任务立即验证，不攒到层末尾
- 验证失败时，根据错误信息修复，最多重试 3 次
- 3 次后仍不通过 → 停止，输出该任务的失败信息和手动修复指引

## change.md 追加格式

所有 wave 完成后，将编码摘要追加到 `$CHANGE_DIR/change.md`（追加，不覆盖已有内容）。

```markdown
---

# 变更 v{N}：编码完成

## 产出文件

- src/a.py（修改）
- src/b.py（新建）

## 执行摘要

| 层 | 任务数 | 完成 | 失败 |
|----|--------|------|------|
| 1 | 2 | 2 | 0 |
| 2 | 2 | 2 | 0 |

## 变更文件清单

| 文件 | 对应任务 | 操作 |
|------|---------|------|
| src/a.py | Task1 | 修改 |
| src/b.py | Task3 | 新建 |
```

### STATE 更新

追加编码摘要后，更新 change.md 顶部的 STATE 块（当前阶段、已完成项、变更文件数）。

## 停止条件

- tasks.md 不存在或格式无法解析 → 停止
- plan.md 不存在 → 停止
- 某任务验证失败且 3 次修复不通过 → 停止，报告失败任务及已完成清单
- 所有层完成 → 更新 change.md，输出完成总结，停止
