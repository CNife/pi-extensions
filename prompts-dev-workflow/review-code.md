---
description: 审阅代码变更是否符合tasks.md计划范围，检查代码质量，追加报告到change.md
argument-hint: "[变更目录]"
---

读取当前变更计划的 `change.md` 最新变更摘要获取文件清单，对照 `tasks.md` 和 `plan.md`，审阅代码变更的目标完成度、范围符合性、代码质量等，追加审阅报告。每次变更最多 3 轮代码审阅（含 fix-code 来回）。

### 变更目录解析

按以下优先级确定当前变更目录：
1. `$ARGUMENTS` 非空 → 直接使用
2. `changes/.active_change` 存在 → 读取其内容作为目录名（去掉首尾空白）
3. 执行 `ls changes/` 找到最近 `YYYYMMDD-*` 子目录 → 向用户确认
4. 以上均无 → 提示用户先执行 `/new-change`

确定后的变更目录记为 `$CHANGE_DIR`，下文所有文件路径均相对于项目根目录。

### 输入

- **变更范围来源**：`$CHANGE_DIR/change.md` 最新变更摘要中的文件清单（N=1 取自「编码完成」，N>1 取自「修复完成」）
- **计划范围来源**：`$CHANGE_DIR/tasks.md` 子任务清单「涉及文件」列
- **目标来源**：`$CHANGE_DIR/plan.md`「目标」节
- **上下文**：`$CHANGE_DIR/change.md` 已有审阅记录

### 审阅流程

1. **确定审阅轮次**：读取 `change.md`，统计已有「代码审阅」节数，当前为第 N 轮（N=已有数+1）。N=1 时基线为最新「编码完成」节，N>1 时基线为最新「修复完成」节。若 N=3，标注为最终审阅。
2. **确定审查范围**：
   - N=1（首次审阅）：以 tasks.md「涉及文件」列为全量范围
   - N>1（修复后审阅）：仅审阅「修复完成」节的变更文件清单中的文件（即本次修复涉及的文件），但 Hard Stops 检查和代码质量检查仍覆盖全项目
3. 读取 `tasks.md` 收集「涉及文件」列，读取 `plan.md`「目标」节
4. **目标完成度检查**：对照 plan.md「目标」，判断代码是否完整实现了目标。标注：✅ 已实现 / ⚠️ 部分实现 / ❌ 未实现 / ➕ 超出目标（实现了计划外的功能）
5. **范围审阅**：逐文件对照 tasks.md「涉及文件」列，标注 ✅ 符合 / ❌ 超出范围
6. **Hard Stops 检查**（🔴 阻断级问题，有一条即不可交付）：
   - 注入漏洞：SQL、命令、路径注入
   - 凭证泄露：密钥、token 硬编码或提交
   - 依赖变更：新增/升级了 plan.md 未声明的依赖
   - 破坏性操作：删除或重命名了计划外的现有文件/接口
7. **运行项目的格式化检查命令**（如 `ruff format --check`、`npm run format`、`cargo fmt --check` 等），记录格式检查结果
8. **运行项目的 lint 检查命令**（如 `ruff check`、`eslint`、`cargo clippy` 等），记录 lint 检查结果
9. **修复循环**（仅针对 format/lint，最多 2 轮）：
   - 若两项均通过 → 跳过修复，直接进入步骤 10
   - Format 不通过 → 运行项目的格式化自动修复命令（如 `ruff format`、`npm run format:fix`）自动格式化
   - Lint 不通过 → 运行项目的 lint 自动修复命令（如 `ruff check --fix`、`eslint --fix`）尝试自动修复
   - 修复后重新运行检查，不通过则进入下一轮
   - 2 轮后仍有残留 → 记录到「未通过项详情」
   - 范围审阅和 Hard Stops 结果不参与修复循环
10. **问题分级汇总**：所有发现的问题按严重程度归类：
    - 🔴 阻断：Hard Stops + 范围超出（不可交付，须进 fix-code 或人工决策）
    - 🟡 建议：目标部分实现、lint 残留（可交付但建议修复）
    - 🔵 注意：格式残留（可自动修复；此处仅记录 2 轮后仍残留的）
11. 追加审阅报告到 `change.md`

### 输出格式

向 `$CHANGE_DIR/change.md` 追加（不覆盖已有内容），版本号顺延：

```markdown
---

# 变更 v{N}：代码审阅（第 N' 轮）

## 审查信息

- 审阅时间：YYYY-MM-DD
- 审阅轮次：第 N' / 3 轮
- 变更文件数：N
- 审查基线：{编码完成 / 修复完成}

## 目标完成度

- 状态：✅ 已实现 / ⚠️ 部分实现 / ❌ 未实现
- 说明：{对照 plan.md「目标」的完成情况}

## 范围审阅

| # | 文件 | 对应任务 | 状态 | 说明 |
|---|------|---------|------|------|
| 1 | src/a.py | Task1 | ✅ 符合 | — |
| 2 | src/b.py | — | ❌ 超出范围 | tasks.md 未列出此文件 |

## Hard Stops

| # | 类别 | 位置 | 问题 |
|---|------|------|------|
| 1 | 凭证泄露 | .env.example | 提交了包含真实 key 的配置 |

## 代码质量

| 检查项 | 命令 | 结果 |
|--------|------|------|
| Format | （项目的格式化检查命令） | 通过 / N 个文件需格式化 |
| Lint | （项目的 lint 检查命令） | 通过 / N 个问题 |

## 总体结论

- **可交付判定**：是 / 否
- 目标完成度：✅ / ⚠️ / ❌
- 范围审阅：通过 / 未通过（N 个文件超出）
- Format：通过 / 未通过
- Lint：通过 / 未通过
- 阻断项：{N 项，逐条列出}

## 未通过项详情

| # | 严重程度 | 类别 | 位置 | 问题 | 处理建议 |
|---|---------|------|------|------|---------|
| 1 | 🔴 阻断 | 范围 | src/b.py | 未在 tasks.md 中 | 更新 tasks.md 或进 fix-code |
| 2 | 🟡 建议 | Lint | src/a.py:42 | 未使用变量 x | 手动删除或加 _ 前缀 |
```

### 下一步指引

审阅报告追加完毕后，根据结论指引下一步：

- **可交付判定=是** → 本次变更代码审查通过，进入 write-test
- **可交付判定=否 且 N<3** → 进入 fix-code，根据本报告修复问题
- **可交付判定=否 且 N=3** → 审阅已达上限，代码存在严重问题，建议重新审视变更方案本身，可能需回到 write-plan

### 约束

- 仅执行文件读取、命令运行、自动格式化/lint 修复和报告写入操作——不做 AI 层面的代码编辑
- 范围判断的唯一依据：变更文件是否出现在 tasks.md 子任务清单的「涉及文件」列中
- Hard Stops 是绝对阻断——有一条即判不可交付
- 若 change.md 中不存在「编码完成」或「修复完成」节，在报告中标注并停止
- 格式检查和 lint 检查独立于范围审阅——即使范围审阅未通过，仍须完成质量检查

### 停止条件

- change.md 中无可匹配的基线节 → 输出报告说明并停止
- tasks.md 或 plan.md 不存在 → 输出报告说明并停止
- 修复循环超过 2 轮 → 记录残留问题，追加报告并停止
- 所有检查完成、报告追加完毕 → 输出下一步指引并停止
