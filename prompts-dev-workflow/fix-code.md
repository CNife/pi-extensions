description: 根据review-code审阅报告与用户讨论确定修复范围，修改代码并更新change.md
argument-hint: "[变更目录]"
---

读取当前变更计划的 `change.md` 最新「代码审阅」报告的未通过项，与用户讨论确定修复范围，执行修复并追加修复记录。

### 变更目录解析

按以下优先级确定当前变更目录：
1. `$ARGUMENTS` 非空 → 直接使用
2. `changes/.active_change` 存在 → 读取其内容作为目录名（去掉首尾空白）
3. 执行 `ls changes/` 找到最近 `YYYYMMDD-*` 子目录 → 向用户确认
4. 以上均无 → 提示用户先执行 `/new-change`

确定后的变更目录记为 `$CHANGE_DIR`，下文所有文件路径均相对于项目根目录。

### 输入

- **审阅报告**：`$CHANGE_DIR/change.md` 最新「代码审阅」节的「未通过项详情」表格
- **上下文**：`$CHANGE_DIR/tasks.md`、`$CHANGE_DIR/plan.md`

### 流程

1. 读取 `change.md`，定位最新「代码审阅」节，提取「未通过项详情」表格
2. 如果没有未通过项（所有问题已在 review-code 修复循环中解决）→ 直接停止，提示用户审阅已通过
3. **展示问题清单**，逐类列出：
   - 🔴 阻断项（范围超出、Hard Stops）
   - 🟡 建议项（目标部分实现、lint 残留）
   - 🔵 注意项（格式残留）
4. **确定讨论模式**：
   - **快速模式**：阻断项均建议修复、建议项默认可跳过时，一次性列出完整清单和推荐处理方式，让用户一次性确认
   - **逐条模式**：问题之间的处理策略有显著分歧时，逐条讨论
5. **讨论修复**：
   - 阻断项 → 必须先处理（快速模式下一并确认）
   - 建议项 → 用户可选择跳过
   - 注意项 → 默认跳过，除非用户特别关注
6. **确定修复清单**：汇总用户确认要修复的项目，向用户确认修复范围
7. **执行修复**：按清单逐项修复代码
   - 范围超出 → 删除超出范围的代码，或将遗漏文件补充到 tasks.md
   - Hard Stops → 消除漏洞、移除凭证、回退依赖等
   - Lint 残留 → 按问题描述修复代码
   - 修复时遵循 tasks.md 和 plan.md 的约束
8. **运行项目的格式化检查和 lint 检查**，确保修复没有引入新问题
9. 追加修复记录到 `change.md`

### 输出格式

向 `$CHANGE_DIR/change.md` 追加（不覆盖已有内容），版本号顺延：

```markdown
---

# 变更 v{N}：修复完成

## 修复决策

| # | 审阅问题 | 严重程度 | 决策 | 理由 |
|---|---------|---------|------|------|
| 1 | src/b.py 超出范围 | 🔴 阻断 | 修复 | 用户确认移除 |
| 2 | src/a.py:42 未使用变量 | 🟡 建议 | 跳过 | 用户认为可接受 |

## 变更文件清单

| 文件 | 操作 | 说明 |
|------|------|------|
| src/b.py | 删除 | 超出范围，移除 |
| src/a.py | 修改 | 修复 lint 问题 |

## 修复后验证

- （项目的格式化检查命令）：通过 / 未通过
- （项目的 lint 检查命令）：通过 / 未通过
```

### 约束

- 每类问题逐一讨论，不批量假设用户意图
- 阻断项不可跳过——若用户坚持不修，明确记录决策和风险
- 修复操作仅限于用户确认的清单，不扩大范围
- 修复后必须重新运行 format/lint 检查

### 停止条件

- 审阅报告中没有未通过项 → 提示审阅已通过，进入 write-test，停止
- 用户确认修复清单后所有修复完成并追加记录 → 输出「进入 review-code」指引并停止
